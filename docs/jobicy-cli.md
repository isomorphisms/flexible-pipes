# SUN JOBICY-CLI-01 execution

`jobicy-cli-open` retains the complete assignment bytes and observes the actual
build host before implementation. `jobicy-cli-acceptance` invokes Kitchen's
real build, installation and installed tests, builds the independent ai-ci
verifier through the pinned ICK driver, rejects an unknown-to-closed status
mutant, and performs a separately identified live Jobicy request.

All roots, exact source heads, program paths and host environment are explicit
parameters. The environment file's digest is captured, and the installed gate
verifies the CLI, Kitchen and ai-ci heads and clean tracked sources. Kitchen
checks exact compiler, JSON, networking and ICK pins. The acceptance stage
records actual executable digests and distinguishes A1/C67 NOT_RUN from the
Linux host. Provisioning remains a preceding distinct operation; these product
stages acquire no dependencies.

The live stage must return the actual installed program's failure when a native
ICU request cannot complete. This leaves the overall pipeline FAIL while its
earlier passing build, installation and fixture/oracle stages remain separately
observed. The owner-readable receipt calls inaccessible live acceptance BLOCKED;
it does not claim that the provider itself is down or that zero stdout records
constitute an empty successful search.

The existing runner is inherited Python migration debt. This job uses its
existing command-stage interface without adding a Python networking client,
verifier or alternate implementation. The parameterized workflow is a local
source-bound execution recipe; checked-in configuration alone is not evidence
that a hosted runner has been provisioned or executed it.
