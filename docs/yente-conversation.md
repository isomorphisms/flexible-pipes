# Yente conversation execution

`pipelines/yente-conversation.json` uses the existing command-stage runner.
It runs a fictional command sequence, constructs a permitted model request,
admits one recorded response through Shallow's executable, and invokes a
separately built ai-ci acceptance executable. The parameters `candidate`,
`state`, `materials`, `commands`, `request`, `response`, and `oracle` name
explicit absolute paths. `session` names a session established by the command
sequence. Use a fresh fictional state directory and request output file for
the demonstration; the independent oracle creates its own cases.

The canonical local invocation is `python3 scripts/run-pipeline
yente-conversation`, with one `--param NAME=VALUE` for each parameter and an
absolute `--runs-root`. The invocation is resolved against this checkout by
the existing runner. Its receipt records this repository revision, the
pipeline digest, resolved argv, exit status, and hashes of actual stage
stdout and stderr. Compilation is an independently recorded prerequisite.

The acceptance program is maintained under
`isomorphisms/ai-ci/examples/autogenerated/yente-conversation/`. It must test
the supplied candidate process instead of importing Shallow's implementation
or trusting a producer's printed PASS. The optional third oracle argument
supplies the exact demonstration commands: the checker reruns them in isolated
state and requires zero error receipts plus a valid, nonempty Yenta transcript.
Candidate, materials, oracle, compiler,
and model/prompt identities belong in the accompanying source-bound evidence.
The runner's command receipt alone does not establish those identities.

This pipeline does not add a generic model-provider protocol. Shallow's
`request` and `accept` modes construct permitted model input and validate a
recorded response. The response must be a strict seven-field plan row. The
request is compared against current permitted context before admission; a
stale request or malformed response must fail the pipeline before acceptance.
Recorded replay and fresh model inference are separate evidence. No provider
endpoint or weights are configured by this pipeline; live inference remains
`NOT_RUN` until an actual model call is observed.

An assistant-authored fictional response is identified as
`assistant-authored-fiction`, with `model=NOT_RUN`; it is never given an
invented model revision. For a replay execution, retain SHA-256 identities of
the command sequence, source response, generated request, policy text, and
compiled candidate/oracle artifacts alongside the FP receipt. Keep those
synthetic fixtures and the actual stage stdout/stderr. This binds the bytes
replayed, not a model inference or production privacy guarantee.

The demonstration and acceptance material are fictional. Production privacy,
authentication, encryption, model quality, and real-person matching do not
follow from successful process-level acceptance.

## Fresh inference

`pipelines/yente-live-conversation.json` uses the same command-stage runner.
Its first stage runs Shallow's checked Ithon trial against the supplied Idriç
candidate, then the separately compiled ai-ci observer checks the retained
prompts, raw outputs, hashes, scope and actual admission. Supply absolute paths
for `ithon`, `trial`, `candidate`, `materials`, a fresh `evidence` directory and
`oracle`. The Ithon interpreter's model runtime must already be provisioned by
Cat Food on the GitHub Ubuntu x86_64 host, with `ITHON_PYTHON` pointing at its
verified interpreter. The pipeline does not install a runtime on a phone.

The fictional sequence includes four audiences, a follow-up, a correction, a
deferral and two exact approved statements in a shared discussion. A separate
bank-only comparison uses the original first-turn request. Its admission status
is reported independently; one comparison is not a quality benchmark. The
small pinned public model is a wiring and behavior control. The observer's
structural checks do not establish tact or interpretation quality. Refused
outputs remain in the evidence, and there is no recorded-answer fallback.
