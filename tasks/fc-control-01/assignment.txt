## Deliverable A: actually converse with a model
1. Keep a configurable transport/provider boundary below `ModelRequest → Transport → ModelEvent`; support a caller-supplied OpenAI-compatible endpoint (including an open-weights backend such as GPT-OSS) without hardcoding model/vendor or credentials in the APK. Retain native C, Idriç semantics, Icky Lua where already owned. Public API authentication is a private runtime capability, never embedded, logged, committed or derived from ChatGPT cookies.
2. Correctly assemble **bounded multi-turn** conversation context from durable canonical history, retaining ordering, explicit failure/uncertainty, cancellation, tools as *data* (never silently executed), provider model identity and no automatic resend. Make Chat Completions and Responses request schemas explicit; never send a Chat Completions body to a Responses endpoint and claim compatibility.
3. Verify the complete flow with actual local TLS fixture: compose → POST → streaming UTF-8 answer → terminal durable journal → close/relaunch → history replay → follow-up turn → correct previous context. Test auth refusal, timeout, malformed JSON, disconnect, stale attempt, cancellation, backpressure and overbound context. Publish exact provider/request/attempt receipts without secrets. Make a guarded real-provider smoke procedure available, but mark it NOT_RUN until an authorized user-supplied model endpoint/credential is exercised.

## Deliverable B: typed FP job controller with first watcher/responder
1. Implement a narrow, inspectable chat-to-work intent boundary for a concrete `STAR/SUN/EARTH/MOON` job and status replies. Separate **drafted/requested** from **accepted FP dispatch** and from **ai-ci completion**. The app must not run raw shell commands or claim issue creation / a chat reply is a job dispatch. Preserve original full job text, work identity and source hash.
2. First watcher/responder **fixture**: accept one explicitly authorized watched source/event, compare durable cursors, construct exactly one bounded typed response/job proposal, require appropriate user authorization for effects, and deduplicate after restart/replay. Use FP's existing identities and delivery/dispatch gates. Never build a second scheduler, a bypass route, or an always-on phone daemon without measured need.
3. Present unambiguous user-facing states for model chat, job request, handoff awaiting visible delivery, authorized dispatch, acceptance and failure. The UI from SUN 1 must remain responsive and useful on A1/C67. Real externally hosted watchers, production callback/notification delivery and broad generalized responder permissions are **not** implied by local fixture PASS; list unqualified stages.
